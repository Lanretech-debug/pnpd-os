## Purpose

This document designs a future Product Delivery Registry writer — a local operational tool for creating a `.pnpd/product-delivery-registry/registry.json` file from a provided entry JSON. It defines the writer model, CLI contract, write semantics, path safety rules, governance boundaries, package/CI policy, fixture strategy, and the future implementation phase.

This document does **not** implement the writer. It does not create `scripts/pnpd-product-delivery-registry-write.mjs`. It does not modify the validator, schema, fixtures, package scripts, CI workflow, or any existing file. It is a design artifact only.

When implemented, the writer will close a critical gap: the Product Delivery registry currently has a schema, fixtures, a validator, artifact reference validation, and hash integrity verification — but no mechanism to create registry data. All registry state remains absent. The writer makes registry creation possible without authorizing any downstream action.

## Current Registry Capability

The Product Delivery registry capability as of baseline `94e6864` includes:

- **Schema**: `.pnpd/product-delivery-registry.schema.json` — committed and tracked.
- **Fixtures**: `tests/fixtures/pnpd/product-delivery-registry/` — 24 shape fixtures (6 positive, 15 negative), 3 artifact-reference fixtures, 4 hash-integrity fixtures, 1 hash support file.
- **Validator**: `scripts/pnpd-validate-schemas.mjs` — supports `--phase 1o`, `--product-delivery-registry <path>`, `--check-registry-artifacts`, and `--verify-registry-artifact-hashes`.
- **Artifact reference validation**: Implemented via `--check-registry-artifacts`. Confirms referenced artifact files exist and are regular files.
- **Hash integrity verification**: Implemented via `--verify-registry-artifact-hashes`. Computes raw-byte SHA-256 of referenced files and compares to recorded `contentHash`.
- **Design docs**: `docs/pnpd/product-delivery-registry-data-convention.md`, `docs/pnpd/product-delivery-registry-artifact-reference-validation-design.md`, `docs/pnpd/product-delivery-registry-hash-integrity-verification-design.md`.
- **Registry directory**: absent. `.pnpd/product-delivery-registry/` is gitignored and does not exist.
- **Registry data file**: absent. `.pnpd/product-delivery-registry/registry.json` is reserved but not created.
- **Registry writer**: absent. No mechanism exists to create registry data.

## Current Writer Gap

The gap is structural and intentional:

- The schema defines what a valid registry looks like.
- The validator confirms whether an existing registry conforms.
- Artifact reference validation confirms whether referenced files exist.
- Hash verification confirms whether `contentHash` matches file bytes.
- But nothing creates the registry in the first place.

Without a writer, registry data can only be created manually or generated by external tooling. The writer provides a governed, predictable path for creating registry data from entry JSON files, with path safety, no-write defaults, and strict governance boundaries built in.

## Design Decision

- **Phase 1O-L is docs-only.** No code implementation.
- Future writer implementation is deferred to:
  `PHASE_1O_M_PRODUCT_DELIVERY_REGISTRY_WRITER`.
- Writer is a **separate script** from the validator.
- Writer does **not** extend the validator with write behavior.
- Writer does **not** extend the dry-run/orchestrator with write behavior.
- The validator remains read-only.
- Orchestrator/runtime consumption remains blocked.

## Selected Writer Model

The future writer is a **dedicated standalone script**:

- **Script path**: `scripts/pnpd-product-delivery-registry-write.mjs`
- **Role**: creates a `.pnpd/product-delivery-registry/registry.json` from a provided entry JSON file.
- **Separation from validator**: the validator reads and checks; the writer creates. These concerns are kept in separate scripts to avoid accidental write paths through validation commands.
- **Separation from orchestrator**: the orchestrator (`scripts/pnpd-orchestrator-dry-run.mjs`) consumes registry data. The writer creates it. The orchestrator remains read-only and dispatch-blocked.
- **No extension of existing scripts**: `pnpd-validate-schemas.mjs` and `pnpd-orchestrator-dry-run.mjs` are not modified for write behavior.

## Future Writer Script Path

```
scripts/pnpd-product-delivery-registry-write.mjs
```

This file does **not** exist in Phase 1O-L. It is reserved for Phase 1O-M or later.

## Future CLI Contract

```bash
node scripts/pnpd-product-delivery-registry-write.mjs \
  --registry .pnpd/product-delivery-registry/registry.json \
  --entry-file <path-to-entry-json> \
  --write
```

### Future flags

| Flag | Required | Purpose |
|---|---|---|
| `--registry <path>` | No | Path to the registry file. Defaults to `.pnpd/product-delivery-registry/registry.json`. Must resolve under `.pnpd/product-delivery-registry/`. |
| `--entry-file <path>` | Yes | Path to a JSON file containing a single registry entry object matching the `entries[]` item shape from the schema. |
| `--write` | See below | Authorizes filesystem mutation. Without it, the writer operates in dry-run/no-write mode. |
| `--no-write` | No | Overrides `--write`. Explicitly prevents any filesystem mutation. |

## No-Write / Write Flag Policy

- **Default is no-write.** If neither `--write` nor `--no-write` is supplied, the writer prints the planned action to stdout and exits without creating any files or directories.
- **Dry-run/no-write mode**:
  - Reads and validates the entry JSON.
  - Composes the full registry in memory.
  - Validates the composed registry through the existing validator.
  - Reports success/failure to stdout.
  - Creates no directories.
  - Creates no files.
  - Does not mutate the filesystem.
- **Write mode** (`--write` alone): the writer creates the parent directory (if needed) and writes the registry file atomically.

## --no-write Override Policy

- `--no-write` always overrides `--write`.
- The combination `--write --no-write` must **not** write to disk.
- This allows CI pipelines and review workflows to safely run with `--no-write` without risking accidental mutation, even if `--write` is present in a shared configuration or alias.

## Registry Path Policy

- **Default path**: `.pnpd/product-delivery-registry/registry.json`
- **Allowed paths**:
  - The default path.
  - Any path that resolves under `.pnpd/product-delivery-registry/` and ends with `registry.json`.
- **Rejected paths**:
  - Absolute paths.
  - Paths containing `..` traversal.
  - URLs.
  - Symlink-escaped paths (must resolve under the registry directory after realpath resolution).
  - Paths outside `.pnpd/product-delivery-registry/`.
- **Parent directory creation**:
  - Allowed only when `--write` is active.
  - The directory `.pnpd/product-delivery-registry/` is gitignored.
  - Generated registry data must never be committed.
- **Registry directory remains gitignored**: the `.gitignore` entry `.pnpd/product-delivery-registry/` is not modified.

## Registry Write Semantics

The initial future writer is **create-only**.

### Create path (registry file does not exist)

1. Validate entry JSON against the registry entry schema shape.
2. Validate `--registry` path against path safety rules.
3. If `--write` is active: create parent directory `.pnpd/product-delivery-registry/` (only if needed).
4. Compose full registry JSON in memory:
   - `schemaVersion`: `"1.0.0"`
   - `recordType`: `"productDeliveryArtifactRegistry"`
   - `registryId`: derived from repo context or provided metadata
   - `createdAt`: current timestamp in ISO 8601 format
   - `createdBy`: from environment or explicit argument
   - `repo`: populated from local git/repo context (repoId, name, branch, commit)
   - `governance`: all authority flags `false`, `advisoryOnly: true`, `ownerFinalAuthority: true`
   - `entries`: single-entry array containing the provided entry
5. Validate composed registry through the existing validator.
6. Write atomically to the target path.
7. Report result.

### Existing registry file path

- If the registry file already exists: **fail**.
- No append mode in first writer.
- No merge mode in first writer.
- No upsert mode in first writer.
- No replace mode in first writer.
- No delete mode in first writer.
- No update mode in first writer.

### Future mutation modes

- Append, merge, upsert, replace, update, and delete modes require separate design and audit phases.
- None are authorized by Phase 1O-L or the future 1O-M implementation.

## Create-Only First Writer Policy

The create-only constraint is deliberate:

- **Simplifies the first implementation.** No diff logic, no merge conflicts, no partial updates.
- **Prevents accidental data loss.** A create-only writer cannot overwrite an existing registry.
- **Forces explicit intent.** The user must decide how to handle an existing registry (manually rename, delete, or wait for a future merge mode).
- **Aligns with governance boundaries.** The registry is local operational state. Creating it is a deliberate action, not an automated side effect.

## Duplicate artifactId Policy

- The first writer creates a registry with a single entry, so duplicate `artifactId` is not a concern at creation time.
- Future append/merge modes must enforce unique `artifactId` across all entries.
- This policy is noted now so the schema and validator are prepared for a future uniqueness constraint if needed.

## Existing Registry File Policy

- If `.pnpd/product-delivery-registry/registry.json` already exists at write time: the writer fails with a clear error message.
- The error message should include the existing file path and state that create-only mode does not support updates.
- The user must decide on a path forward: move/rename the existing file, delete it (if intended), or wait for a future append/merge mode.

## Atomic Write Policy

The writer must use atomic write semantics:

- Compose the full registry JSON in memory.
- Write to a temporary file in the same directory (e.g., `registry.json.tmp.<random>`).
- Rename the temporary file to the target path.
- On failure, clean up the temporary file.
- This prevents partial writes and ensures the registry file is either fully present or fully absent — never incomplete.

## Entry Input Policy

- The writer accepts exactly **one** entry JSON file via `--entry-file`.
- The entry JSON must match the `entries[]` item shape from the registry schema.
- The entry JSON is **not** a full registry — it is a single entry object with:
  - `artifactId`, `artifactType`, `phase`, `path`
  - `validation` (validator, mode, status, validatedAt, path, exitCode)
  - `createdAt`, `createdBy`
  - `source` (sourceType, sourceRef)
  - `notes` (optional)
  - `integrity` (hashAlgorithm, contentHash)
- CLI sprawl is avoided: the writer does not accept individual `--artifactId`, `--artifactType`, `--path`, `--hash`, etc. flags. All entry data comes from the JSON file.
- This keeps the CLI surface small and the entry data self-documenting.

## Top-Level Registry Scaffolding Policy

The writer composes the top-level registry scaffolding. The user provides only the entry; the writer provides:

- `schemaVersion`: `"1.0.0"` (hardcoded constant matching the schema).
- `recordType`: `"productDeliveryArtifactRegistry"` (hardcoded constant matching the schema).
- `registryId`: derived from repo context (e.g., repo name from `package.json` or `.git/config`).
- `createdAt`: ISO 8601 timestamp at write time.
- `createdBy`: from environment variable `PNPD_CREATED_BY`, git user name, or explicit `--created-by` flag.
- `repo`: populated from local git context:
  - `repoId`: from `package.json` name or git remote origin path.
  - `name`: from `package.json` name or repo directory name.
  - `rootRelative`: `"."` (always; the registry lives in repo root).
  - `branch`: current git branch.
  - `commit`: current git HEAD commit hash.
- `governance`: hardcoded with all authority fields `false`:
  - `advisoryOnly: true`
  - `authorizesImplementation: false`
  - `authorizesMerge: false`
  - `authorizesDispatch: false`
  - `authorizesDeployment: false`
  - `authorizesGitHubMutation: false`
  - `authorizesApiMutation: false`
  - `certifiesProductionReadiness: false`
  - `ownerFinalAuthority: true`
  - `codexIsOwner: false`
  - `agentBridgeCanApprove: false`, `agentBridgeCanMerge: false`, `agentBridgeCanDispatch: false`, `agentBridgeCanDeploy: false`
  - `runtimeConsumptionAllowed: false`
  - `artifactGenerationAllowed: false`
  - `externalMutationAllowed: false`
- `entries`: a single-element array `[entry]`.

Repo metadata must be populated **only from safe, deterministic local sources** (git, package.json). No network calls. No API requests. No external process invocations beyond `git rev-parse` and `git branch --show-current` or equivalent Node APIs.

## Hash / contentHash Policy

- The writer does **not** derive `contentHash` values in the first implementation.
- The entry JSON must include an `integrity` block.
- If `hashAlgorithm` is `"sha256"`, the caller must provide `contentHash` in the entry JSON.
- If `hashAlgorithm` is `"none"`, `contentHash` must be `null`.
- The writer composes and writes the registry. Hash verification is a separate, optional step performed by the existing validator:
  ```bash
  node scripts/pnpd-validate-schemas.mjs \
    --product-delivery-registry .pnpd/product-delivery-registry/registry.json \
    --check-registry-artifacts \
    --verify-registry-artifact-hashes
  ```
- **Writer composes; validator verifies.** These are distinct tools with distinct responsibilities.
- A future hash helper or hash precompute tool is out of scope for Phase 1O-L and 1O-M.

## Artifact Reference Validation Policy

- The writer **may** invoke the existing registry validator on the composed registry as part of write validation.
- Whether the writer runs artifact reference checking (`--check-registry-artifacts`) and hash verification (`--verify-registry-artifact-hashes`) as part of its pre-write validation is a future implementation decision for 1O-M.
- The writer must **not** parse or validate referenced artifact contents.
- The writer must **not** invoke validators for the referenced artifact body.
- The writer must **not** infer or certify artifact quality from any validation step.

## Hash Verification Policy

- The writer may optionally run hash verification as a pre-write gate.
- If enabled, hash verification uses the existing validator with `--check-registry-artifacts --verify-registry-artifact-hashes` on the composed in-memory registry (written to a temp file if needed).
- Hash verification failure should cause write failure.
- Hash verification is **not required** by default. The caller can skip it if the entry is not yet ready for hash verification.

## Referenced Artifact Content Validation Boundary

- **The writer does not validate referenced artifact content.**
- The writer confirms the entry JSON conforms to the entry schema shape.
- The writer may confirm the referenced artifact file exists (via artifact reference validation).
- The writer may confirm the hash matches (via hash verification).
- The writer does **not** open, parse, schema-validate, or semantically inspect the referenced artifact file.
- Referenced artifact content validation remains a separate future capability.
- The writer must not import, call, or depend on artifact content validators.

## Registry Writer Governance Boundary

The writer creates **local operational state only**. It must not:

- Authorize implementation.
- Authorize merge.
- Authorize dispatch.
- Authorize deployment.
- Authorize GitHub/API mutation.
- Authorize runtime consumption.
- Authorize release.
- Authorize artifact generation.
- Generate or claim production certification.
- Call external services or network endpoints.
- Run external processes beyond safe local git inspection.

All governance fields in the composed registry are hardcoded to `false` (except `advisoryOnly` and `ownerFinalAuthority`). The writer cannot be used to create a registry that authorizes any downstream action.

## Runtime Consumption Boundary

- **Runtime consumption remains blocked.**
- The writer creates registry data. It does not consume registry data at runtime.
- The orchestrator (`scripts/pnpd-orchestrator-dry-run.mjs`) reads `.pnpd/repos.example.json`, not `.pnpd/product-delivery-registry/registry.json`.
- No runtime path currently reads the product delivery registry.
- A future runtime consumption design must be separate from the writer design.

## Dispatch / Deploy / GitHub API / Production Boundary

- **Dispatch remains blocked.** The writer does not trigger, schedule, or authorize orchestration dispatch.
- **Deployment remains blocked.** The writer does not deploy, stage, or prepare artifacts for deployment.
- **GitHub/API mutation remains blocked.** The writer makes no HTTP calls, no API requests, and performs no Git operations beyond local inspection.
- **Production certification remains blocked.** The writer does not certify, claim, or imply production readiness. The composed registry's `governance.certifiesProductionReadiness` is always `false`.

## Product Design Integrity / Asset Decisioning Boundary

- **Product Design Integrity / anti-slop governance** remains a separate future track.
- **Product Design Asset Decisioning** remains a separate future track.
- Neither is designed, implemented, or authorized in Phase 1O-L or the future 1O-M writer implementation.

## Package / CI Policy

- **No package changes in Phase 1O-L.** `package.json` is not modified.
- **No CI changes in Phase 1O-L.** `.github/workflows/pnpd-ci.yml` is not modified.
- The future writer should **not** be invoked by default package scripts (`npm run validate`, `npm test`) unless separately designed and approved.
- The future writer should **not** run automatically in CI by default.

## Risks and Mitigations

### Risks

1. **Create-only limitation may surprise users.** Users expecting append/merge behavior may be frustrated when the writer refuses to touch an existing registry. Mitigation: clear documentation, error messages, and a future 1O-N append/merge design phase.

2. **Registry scaffolding may not match user expectations.** Auto-populated repo metadata (branch, commit) may not reflect what the user intended. Mitigation: dry-run mode prints the composed registry before writing, allowing review.

3. **No hash auto-computation may lead to incorrect hashes.** Users providing `contentHash` manually may mistype or use the wrong file. Mitigation: hash verification is available as a separate step; future hash helper tool may be designed.

4. **Governance block is hardcoded to `false` in all authorizing fields.** Users cannot create a registry that authorizes any downstream action. This is intentional and aligns with governance invariants, but users expecting flexibility may be surprised. Mitigation: clear documentation; authorizing fields are unlocked only through separate owner-governed design phases.

5. **Future writer drift into content validation.** The proximity of the writer to the validator creates a risk that the implementer adds artifact content validation under the writer. Mitigation: explicit boundary sections in this document; Codex audit of the implementation.

### Mitigations

- **Create-only policy** explicitly documented and enforced.
- **Dry-run/no-write default** allows review before write.
- **Atomic write** prevents partial corruption.
- **Governance hardcoding** enforced at the code level (const values, not user-provided).
- **Separate writer from validator** prevents accidental write paths through read commands.
- **Codex audit required** before merge.
